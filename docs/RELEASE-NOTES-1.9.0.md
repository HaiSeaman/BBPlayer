# BBPlayer 1.9.0

**一句话**：这是一个**打磨与提速**版本——把内核从已经"停售后"的 Electron 34 换到最新的 **44.7.0**（开窗更快），并修掉 **3 个并发竞态缺陷**（其中 2 个会让画面/声音悄悄错乱），顺手压掉 2 处运行时开销（另 1 处尝试后主动回退）。**没有加新功能**，目的就是让播放更稳、更省。

---

## ⚙️ 内核升级：Electron 34 → 44（34 已停售后）

Electron 官方**早就停止维护 34 这条线**了（37 版发布时即公告 "End of Support for 34.x.y"）。本版升到当前最新的稳定版 **44.7.0**，正好吃到官方在 42+ 才合入的**三个启动优化**：

| 官方优化 | 效果（官方数据，Linux/x64 基准） |
|---|---|
| 主进程 Node 启动快照 | 启动到就绪 **197.8ms → 148.7ms（快 25%）** |
| js2c 构建期代码缓存 | 渲染进程初始化 **9.8ms → 6.4ms（快 35%）** |
| preload 字节码缓存 + 通信预推 | 首屏 **244ms → 140ms** |

BBPlayer 主进程只有不到 700 行、零 npm 依赖，正是这类优化**最受益**的形态。

**安全性核对**：34→44 之间 Electron 的破坏性改动（渲染端移除 clipboard、停止支持 macOS 12、ANGLE 静态链接、网络请求校验、移除 32 位构建）已逐条静态核对，**与本项目零冲突**——本项目不读剪贴板、不发网络请求、只发布 64 位 Windows 版。

配套把打包工具 `electron-builder` 从 25.1.8 升到 26.17.0，顺手清掉了 `npm audit` 报出的 **1 个严重 + 16 个高危**（都在打包工具链的传递依赖里，**不会进到软件本体**）。

## 🔧 修复的 3 个竞态缺陷（都是"偶发、难查、看着像玄学"的那类）

### 1. 拖入字幕解码时换片：旧字幕被挂到新视频上（并且新片字幕被永久压制）

**你能感觉到的现象**：你把字幕文件拖进画面后，趁它还在解码的零点几秒内点了另一部片子——结果**新片子上挂着上一部的字幕**，而且从此以后**这部新片再也自动加载不出自己的字幕**。

**原因**：字幕解码要读文件（有等待）。代码在"读完文件"之后直接往**当前**画面上贴，没有核对"我还是当初那部片子吗"。等待期间你换了片，"当前"早就变了，于是旧字幕贴到了新片身上；同时它还把"这部片的手动字幕"这个标记写脏了，导致新片自己的同名自动字幕被判为"用户配过了、别动"，再也不加载。

**修复后**：拖入时先记下"发起时的视频"，贴字幕前先比对，不一致就整条丢弃。同一个函数家族里另一条路径（从菜单选字幕）本来就有这层校验，这次把漏掉的那条补上。

### 2. 音频探测少查一道"加载序号"，慢探测会落到新的加载上

**你能感觉到的现象**：极少数情况下，一部"有画面没声音"的片子触发了自动探测，你在探测的 3 秒等待里切了片 / 或同一部片被重开，旧探测回来时会把结论套到**新的**那次播放上。

**原因**：判断"这次探测还有效吗"时，代码只比了"文件路径一样不一样"。但**同一个路径被重新加载**（加载失败自动跳回、或清空后重开）时路径是一样的，序号却已经变了——只比路径分辨不出这种情况。同家族另一个探测函数早就有"比对加载序号"的纪律，这个漏了。

**修复后**：安排定时器时记下当时的加载序号，回调一进来就先比对，对不上直接放弃。

### 3. 快速连切视频会泄漏"续播"监听器，越切越卡

**你能感觉到的现象**：**频繁快速切换视频**（比如连点 20 部片）之后，播放器内部会积着一批"作废的回调"，之后每次开始播放都要空跑一遍，属于慢性拖慢。

**原因**：每次播放都会挂一对"等元数据 / 等失败"的临时监听器，靠这两个事件来把自己摘掉。但**"上一部还没加载完就被下一部打断"**时，浏览器只发"清空 / 中止"事件，**不发**这两个事件——这对监听器就永远等不到自己的信号，一直挂在身上。实测快速连切 20 次会泄漏 **40 个**监听器。

**修复后**：改成"单例"——新的一次加载先把旧的那对主动摘掉，任何时刻最多只有一对在挂。实测连切 20 次**净泄漏 0 个**，而且续播功能行为不变（有历史的片子照样弹续播提示）。

> 这三条都补了会抓住它们的自动化断言，并做了"先还原成缺陷 → 测试确实失败 → 再修回来 → 通过"的红绿验证，确认测试真有分辨力。

## ⚡ 运行时开销收敛（逻辑零变化，只省资源）

1. **鼠标移动热路径合帧**：功能栏显隐判断里有一次"读取布局尺寸"的**强制同步重排**。高回报率鼠标（1000Hz）下每秒能触发上千次。改成"一帧只处理最后一次"（和窗口拖拽同一套做法），逻辑不变、开销大减。
2. **截图位图立即释放**：一张 4K 截图约 **33MB** 的位图，导出后**立刻清空画布**，不等垃圾回收——连续截图的内存峰值从"张数 ×33MB"压回"单张"量级。
3. **频谱渐变：尝试优化后主动回退**（如实记录）：曾想把每帧重画的 32 条渐变缓存起来，但代码审查发现安静段的矮柱（3px 基座）会落在固定渐变的最暗端、**几乎看不见**——属视觉回归，已**回退成原来的逐帧绘制**，并在代码里写明了原因。GC 代价经审计定级为"可忽略"，**画面保真优先**。

## ⚠️ 如实说明

- **本版没有新功能**，是一次稳定性与启动速度的打磨。
- **已知遗留（本版有意未动）**：
  - **多窗口的设置/历史会互相覆盖**——每个窗口各存一份，后保存的盖掉先保存的。根治要把存档集中到主进程，属架构级改动。
  - **转换失败只提示原因，没有"用其它播放器打开"的按钮**——那是新功能，不在本版夹带。
  - **边转边播、多音轨选择、内嵌字幕烧录**：仍按原计划未做（理由见开发文档）。
- **老格式播放速度取决于机器**：有独显走硬件编码会快很多；本机测试环境因驱动版本比 ffmpeg 要求低一档，自动退回软件编码（1080p 约 8.5 倍速、DVD 约 30 倍速、最坏约 1.6 倍速）——只影响第一次等待，不影响播放。
