# BBPlayer 1.8.0

**一句话**：这个版本让 BBPlayer 能播以前打不开的老格式了——**RMVB / AVI / FLV / WMV / TS / VOB / MPG 等 11 种格式，现在双击就能看**。同时修掉了 **13 个真实缺陷**（其中 5 个会直接毁掉使用体验：换片卡半分钟、字幕换不了、网络盘上的片子被误报成损坏、大屏换小屏后窗口关不掉、缓存删错文件），并把自动化测试从"几乎没有"补到 **67 项**。

---

## 🎬 新功能：老格式也能播了

以前遇到 `.rmvb`、`.avi`、`.wmv` 这类文件，BBPlayer 只会提示"无法解码"。现在它内置了一个 **LGPL 版 FFmpeg**，会按"代价最小"的方式自动处理：

| 档位 | 什么时候用 | 要等多久 |
|---|---|---|
| **只换容器** | TS / M2TS / FLV(H.264) / AVI(H.264) 这类"外壳不认、画面编码没问题"的 | **不到 1 秒**，画质零损失 |
| **只换音频** | 画面正常、但音轨是 AC3 / EAC3 / DTS 的（**很多高清片源"有画面没声音"就是这个原因**） | **不到 1 秒**，视频零损失 |
| **重新编码** | RMVB / WMV / Xvid(DivX) / MPEG-1/2（VOB、MPG）/ Theora / ProRes / H.263 等老编码 | 要等（1080p 大约 2～10 倍速），有轻微画质损失 |

配套做好的事：

- **进度实时可见**，而且会明确告诉你这次是"正在换容器"（秒级）还是"正在重新编码"（要等）——不用猜；
- **转好的文件会缓存**，同一部片**第二次打开秒开**；
- **随时切走就取消**，不会留下后台进程偷跑 CPU；
- **运行时兜底**：万一探测说"能播"、实际却黑屏或没声音（比如 MKV 里装了 DTS、mp4 里装了 Xvid），软件会自己发现并改成转换，每个文件只兜一次，不会来回折腾；
- **内置转换器缺失时自动降级**：这些老格式会明确提示原因，其它格式完全不受影响。

支持的格式总数从 14 种增加到 **25 种**（8 原生视频 + 11 需转换视频 + 6 音频），全部支持双击文件关联打开。

## 🔧 修复的 8 个真实缺陷

### 1. 换片时旧转换任务"作废失效"——新片被堵 37.8 秒（最严重）

**你能感觉到的现象**：打开一部需要转换的长片（比如 10 分钟的 RMVB），等了两秒觉得太慢，换去点另一部短片——结果**短片迟迟不出来**，界面像卡住一样。实测修复前短片要等 **37.8 秒**。

**原因**：代码里"记下当前任务编号"这一行，不小心写在了"探测文件"**之后**。而探测是最慢的一步。于是时间线变成：长片开始探测 → 你换片（编号 +1）→ 长片探测完**才**去读编号，读到的已经是**新的编号**，就误以为自己还有效，于是把整个长片完整转码，把你在等的短片堵在后面（转换队列同时只跑 1 个）。

**修复后**：短片 **436 毫秒**就出来了（快了约 87 倍），长片任务被正确作废。

### 2. 字幕菜单"换了字幕却提示失败"，而且之后再也换不了

**现象**：你给某部片子拖入过字幕，之后想从菜单里换另一个字幕文件，会提示"加载字幕文件失败"——**而且从此以后这个视频都换不了字幕**。

**原因**：代码里有道"手动配的字幕优先，别被同名字幕顶掉"的保护，本意很好，但被放在了错误的函数里——菜单加载走的是同一个函数，于是把自己的手动操作也拦住了。

**修复**：把这道保护挪到"同名自动加载"专属的位置；菜单加载成功后反过来登记一下。手动优先的效果一点没丢。

### 3. 视频放在网络盘/U 盘上时，"卡住"会被误报成"文件坏了"

**现象**：视频放在掉线的网络位置、被拔的 U 盘、或有坏道的盘上，转换时卡住了——软件只告诉你"无法解析媒体源"，你会以为是文件损坏，其实是**读取卡住超时**了。

**原因**：软件有个"120 秒没反应就放弃"的保护（防止卡死时占住 CPU）。但它中止后报出的错误，和"用户主动取消"用的是同一种——于是这个真实原因被当成"用户取消"静默吞掉了。

**修复**：现在能区分两者，会明确告诉你"转换超时：源文件 120 秒无任何响应，可能所在的磁盘/网络位置已断开或存在坏道"。

### 4. 从大屏换到小屏后，窗口关不掉

**现象**：在 4K 显示器上用软件、保存了窗口大小，之后换到 1080p 笔记本打开——窗口比屏幕还宽，而**关闭按钮画在窗口右上角**（无边框窗口自绘的），直接落到屏幕外面，**关不掉也拖不动**。

**原因**：窗口状态恢复时只检查了"左边那一片还在屏幕上吗"，没检查"窗口是不是比屏幕还大"。

**修复**：现在会把窗口尺寸收进当前屏幕范围内。

### 5. 缓存会自动删错文件（本地硬盘上）

**现象**：转换产生的临时文件攒多了会自动清理。按设计应该删"最久没看的"，但在 Windows 上变成了"删最老的"——**你天天在追的那部老剧，产物反而先被删掉**，下次打开又要重新转一遍。极端情况下甚至可能删掉你**正在看**的那个，拖进度条就失败。

**原因**：判断"多久没看"用的是系统的"最后访问时间"，但 Windows 的 NTFS 默认**不记录**这个时间（实测读取文件后该时间完全不变）。

**修复**：改成软件自己记录"这个产物上次什么时候被用过"，不再依赖系统的不可靠时间戳。

## 🔧 其余修复（8 条）

**6. 转换产物没有体积上限**（文档说了，代码里其实没有）
理论上估算不准时可能一直转、把磁盘写满。现在加了 16GB 的单文件闸门。这里有个坑实测踩过：ffmpeg 自带的 `-fs` 参数一超限就异常退出、**产物还不落地**，等于转半天白扔。所以改成实时监控 ffmpeg 自己上报的字节数、超了主动停——实测 1 秒内拦住，半截碎片也清干净。

**7. 子进程收尾不幂等 → 可能漏杀 ffmpeg，留下吃 CPU 的僵尸进程**
实测发现：spawn 失败时 `error` 和 `close` **两个事件都会触发**，导致清理逻辑跑两次，第二次会把"新任务的进程登记"抹掉——之后再也杀不掉它。已加幂等保护。

**8. 转码进程没有降优先级**（文档承诺了，代码没做）
重编码很吃 CPU，占满一个核时会让整机操作发涩。现在会把转码进程优先级降到"低于正常"。调不动就忽略——只影响流畅度，绝不让转换失败。

**9. 进度文案和文档对不上**
README 写的是"正在换容器… 45%"，实际只显示笼统的"正在转换格式"，你没法区分"1 秒"还是"等几分钟"。现在会显示真实档位。

**10. 主进程又有同步读盘**（违反项目自己定的纪律）
新增的几个接口又用了同步 `fs.existsSync`。多窗口并存时，同步读盘等于把所有窗口的按钮一起卡住。已统一改成异步。

**11. 播放列表均衡器性能问题**
播放/暂停时，标记挂在**整个列表**上，导致列表里每一行的动画样式都要重算（500 条 = 1500 个子元素），而实际上只有当前那一行在动。已收敛到当前条目。

**12. "先只换音频、后又要重编码"的文件，第二次打开还会黑屏一次**
软件会优先复用之前转好的产物。但复用顺序写反了：它会优先捡起那个"只换了音频"的版本——而那个版本恰恰是因为**画面也解不出**才被淘汰、改成重新编码的。已调整顺序。

**13. 文件夹嵌套太深时，深层的视频会静默消失**
打开文件夹时会扫描里面的视频，但嵌套超过 4 层就不往里看了，**而且不告诉你**——你以为"这个文件夹就这些片子"。现在会如实提示"未全部载入"（和文件数量太多时的提示一致）。

## 🧪 工程质量：自动化测试从"几乎没有"补到 67 项

以前只有"语法检查 + 扩展名对账"，2600 行的界面代码完全没有自动化测试——而这类框架最容易出的恰恰是**静默失效**（顶层脚本抛错被吞掉、界面元素改了名导致功能失效）。

这个版本补齐了三套**无界面自检**（`npm run verify` 一条命令全跑）：

| 脚本 | 做什么 |
|---|---|
| `verify-converter.js`（35 项） | 判定规则单测 + **自带样本的真实转换**：换片作废、产物真实落地、缓存命中、体积闸门；以及看门狗错误分类、缓存淘汰依据、产物复用顺序的盯防 |
| `verify-renderer.js`（32 项） | 用 Node `vm` + DOM 桩**真实执行 renderer.js**：设置恢复完整性、10 种真实畸形字幕、播放列表索引、失败熔断、音乐模式、兜底防竞态 |
| `verify-wiring.js` | 手写契约对账：打包清单、preload 暴露的 API ↔ 实际调用、IPC 通道收发双向；以及窗口钳制、目录截断标记的盯防 |

两个关键设计：

1. **测的是真代码**，不是复制出来的副本——否则"改了产品代码但忘了同步测试"就会变成假成功；
2. **关键行为自带样本**：旧版把"换片作废 / 产物落地 / 体积闸门"全塞在"需要外部样本"的分支里，默认环境下一条都跑不到，等于没有保护。**上面那个"堵 37.8 秒"的严重缺陷正是因此长期没被发现**。现在这些用例自己造样本，只要内置 ffmpeg 在就会跑。

每条修复都做了**红-绿验证**：把修复还原成缺陷状态 → 测试确实失败 → 恢复 → 通过。确认测试真有分辨力，不是摆设。打包产物也做了校验——`app.asar` 里的源文件与工作区**逐字节哈希一致**，确保打进 exe 的确实是修复后的代码。

## ⚠️ 如实说明

- **内部转换器是 LGPL 版 FFmpeg**，以独立进程方式调用（不链接、不修改），许可证文本随程序分发。
- **老格式的播放速度取决于你的机器**：有独显的机器会走硬件编码（快得多），本机测试环境（GTX 1660 Ti）因为驱动版本比 ffmpeg 要求低一档，自动退回软件编码——实测 1080p 约 8.5 倍速、DVD 约 30 倍速、最坏情况约 1.6 倍速。转换速度不影响播放，只影响第一次等待时间。
- **本版未做**（有意，避免夹带新功能）：升级 Electron 内核、多窗口设置互相同步、外部播放器一键接管、边转边播。每一项的理由都写在 `docs/DEVELOPER.md` 的 v1.8.0 遗留事项里。
